    So schützt man sich
    
      
    
        
    1Prepared Statements
    Die Abfrage und die Eingaben werden getrennt übergeben. Eingaben bleiben Daten und werden nie zu SQL-Code.
    
        
    2Passwörter hashen
    Nie im Klartext speichern, sondern mit einem Verfahren wie bcrypt oder Argon2. Dann bringt ein Datenleck deutlich weniger.
    
        
    3Rechte & Fehler begrenzen
    Datenbanknutzer mit minimalen Rechten verwenden, Eingaben prüfen und keine technischen Fehlermeldungen an Nutzer ausgeben.

    Reine Simulation: Die „Datenbank“ ist eine Liste im Browser, es werden keine Daten gesendet oder gespeichert.
    Jede geöffnete Seite hat ihren eigenen Sitzungszustand. Änderungen wie DROP TABLE gelten nur für diese Seite
    und sind für andere Personen oder Tabs nicht sichtbar; beim Neuladen wird die Datenbank zurückgesetzt.
    Simuliert wird SQL im Stil von SQLite (Kommentare mit --, # und /* */).
    SQL-Injection gegen fremde Systeme kann strafbar sein (z. B. §§ 202a, 303a StGB) – probiere sie nur an eigenen Testsystemen aus.
